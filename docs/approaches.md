# Alternative Approaches for Minecraft Text-to-Audio Generation

## Context

- **Current model:** AudioLDM2 (diffusion-based) fine-tuned with LoRA on UNet cross-attention
- **Dataset:** 195 raw .ogg → 325 augmented clips (277 train / 48 val)
- **Problem:** LoRA and last-layer fine-tuning produce poor results. Full fine-tuning needed ~2600 epochs for marginal quality. The domain gap between pretrained natural audio and Minecraft's 8-bit/lo-fi aesthetic is too large for parameter-efficient methods.

---

## Approach 1: Content Generation + Minecraft Style Transfer

**Core idea:** Use a pretrained text-to-audio model as-is to generate the semantically correct sound (zombie growl, footsteps, etc.), then pass it through a separately trained style transfer network that converts any audio into Minecraft's sonic signature.

**Why it works:** The pretrained model already understands "zombie growl" — it just doesn't know Minecraft's zombie growl. The style gap (lo-fi, 8-bit-ish, synthetic timbre) is a simpler mapping to learn than the full text→Minecraft audio pipeline.

**Architecture:**

```
Text Prompt → AudioLDM2 (frozen) → Realistic Audio → Style Transfer Net → Minecraft Audio
```

The style transfer network can be:
- **Option A — Convolutional autoencoder:** Train an encoder-decoder on mel spectrograms. Input: mel of realistic audio. Target: mel of matching Minecraft sound. Use L1 + perceptual loss (CLAP embeddings of output vs target). ~2-5M params.
- **Option B — CycleGAN for audio:** Unpaired style transfer. Domain A = realistic sounds (generated by AudioLDM2). Domain B = your 325 Minecraft clips. No need for aligned pairs. Uses adversarial + cycle-consistency loss on mel spectrograms.
- **Option C — Deterministic DSP baseline:** Bit-crush (reduce to 8-bit), downsample to 11kHz→resample back to 16kHz, apply band-pass filter (200Hz–4kHz), light distortion. No training. Use as baseline to see how far pure signal processing gets you.

**Training data for style transfer:**
- Generate 325 realistic audio clips using vanilla AudioLDM2 with your existing captions
- Pair them with the corresponding Minecraft processed clips
- Train on (realistic, minecraft) pairs → the network learns the style mapping

**Libraries:** `torch`, `torchaudio`, existing AudioLDM2 pipeline for generation, HiFi-GAN or Griffin-Lim for mel→waveform if needed.

**Compute:** Very light. The style transfer net is tiny. Trains in minutes on a T4.

**Steps:**
1. Generate baseline audio for all 325 captions using vanilla AudioLDM2
2. Build paired dataset: `(baseline_wav, minecraft_wav)` for each caption
3. Compute mel spectrograms for both
4. Train convolutional autoencoder: input=baseline mel, target=minecraft mel
5. At inference: generate with AudioLDM2 → pass through style net → vocoder → output

**Pros:** Leverages pretrained model fully, small trainable component, fast iteration.
**Cons:** Two-stage pipeline adds complexity; style net quality caps the output.

## Approach 2: Fine-tune AudioGen / AudioCraft (Autoregressive)

**Core idea:** Switch from diffusion (AudioLDM2) to Meta's autoregressive AudioGen. It generates audio as discrete codec tokens (via EnCodec), and fine-tuning autoregressive models on small datasets is a much more tractable problem.

**Why it works:**
- Autoregressive next-token prediction gives direct, per-token supervision (cross-entropy loss) — much stronger gradient signal than diffusion's MSE on noise predictions
- EnCodec's discrete token space is inherently lower-resolution, which naturally aligns with Minecraft's lo-fi aesthetic
- Standard LM fine-tuning recipes (low LR, weight decay, short warmup) are well-established and reliable on small data

**Architecture:**

```
AudioGen architecture:
Text → T5 encoder → Cross-attention → Transformer decoder → EnCodec tokens → EnCodec decoder → Waveform

EnCodec tokenization:
Audio (16kHz mono) → EnCodec encoder → 4 codebooks × 50 tokens/sec → discrete token sequence
4 seconds of audio = 4 × 200 = 800 tokens
```

**Model:** `facebook/audiogen-medium` (1.5B params) from the `audiocraft` library. There's also `facebook/musicgen-small` (300M) which has a similar architecture if you want something lighter — it's trained on music but the architecture and fine-tuning procedure are identical.

**Fine-tuning approach:**
- Freeze T5 text encoder (it already understands language)
- Fine-tune the transformer decoder (the autoregressive token predictor)
- Use LoRA on the decoder OR full fine-tune with low LR (1e-5 to 5e-5)
- LoRA actually works well here because the token prediction task is closer to the pretrained distribution than diffusion latent prediction was
- AudioCraft has built-in fine-tuning support via Dora/Hydra configs

**Training details:**

| Parameter | Recommended |
|-----------|-------------|
| Base model | `facebook/audiogen-medium` |
| LR | 1e-5 (full FT) or 1e-4 (LoRA) |
| Batch size | 4–8 (with grad accum) |
| Epochs | 50–200 (monitor val loss) |
| LoRA rank | 16–32 (can afford higher with AR model) |
| Max audio length | 4s (200 tokens per codebook) |
| Optimizer | AdamW, weight decay 0.01 |
| Scheduler | Cosine with 10% warmup |

**Setup:**

```bash
pip install audiocraft encodec
```

```python
from audiocraft.models import AudioGen
from audiocraft.data.audio import audio_write

# Load pretrained
model = AudioGen.get_pretrained('facebook/audiogen-medium')
model.set_generation_params(duration=4.0)

# Generate baseline (before fine-tuning)
descriptions = ['minecraft zombie growling sound effect']
wav = model.generate(descriptions)  # (1, 1, 64000) at 16kHz
audio_write('output', wav[0].cpu(), model.sample_rate)
```

**AudioCraft fine-tuning has two paths:**

**Path A — Use AudioCraft's built-in training (recommended):**
- AudioCraft uses Hydra configs + Dora for experiment management
- Prepare dataset in AudioCraft's expected format: folder of .wav files + .txt caption files (same name)
- Write a Hydra config overriding the dataset path and training params
- Run: `dora run -d solver=audiogen/audiogen_base_16khz model/lm/model_scale=medium datasource.train=your_data`

**Path B — Manual fine-tuning loop (more control):**
- Extract the `lm` (language model) component from AudioGen
- Tokenize all your .wav files through EnCodec
- Train the LM on (text_condition, token_sequence) pairs with standard cross-entropy loss
- This gives you full control over the training loop, LoRA application, etc.

**Dataset preparation:**
```
data/audiocraft_format/
  zombie_hurt.wav       + zombie_hurt.txt  ("minecraft zombie getting hurt sound effect")
  cave_ambience.wav     + cave_ambience.txt ("minecraft cave ambience sound effect")
  ... (325 pairs)
```

**Compute:** AudioGen-medium (1.5B) fits on a T4 16GB with gradient checkpointing + FP16. Training 325 clips for 100 epochs ≈ 2-4 hours on T4.

**Pros:** Strongest theoretical fit for small-data fine-tuning. Discrete tokens suit Minecraft aesthetic. Well-supported library.
**Cons:** Switching base models means rewriting train/infer code. AudioCraft's Hydra/Dora system has a learning curve.

## Approach 3: Prompt Engineering + DSP Post-Processing (No Training)

**Core idea:** Get the pretrained model to produce closer-to-Minecraft output through better prompts, then apply deterministic signal processing to close the remaining gap. Zero training required.

**Why it works:** Minecraft sounds have a very recognizable sonic fingerprint that can be largely replicated through DSP: low sample rate, limited bit depth, narrow frequency range, specific reverb characteristics. If the pretrained model can get the content right, DSP handles the style.

**Prompt strategy:**
- Add style descriptors: "8-bit retro video game zombie growl, low fidelity, pixelated sound, chip-tune style"
- Add negative guidance (AudioLDM2 supports negative prompts): "high fidelity, realistic, orchestral, cinematic"
- Increase guidance scale (try 5.0–7.5) to push harder toward the prompt
- Try multiple prompt templates and cherry-pick best results

**DSP chain (applied to generated audio):**

```python
import numpy as np
import librosa
import soundfile as sf

def minecraft_ify(audio, sr=16000):
    # 1. Bit-crush: reduce to ~8-bit equivalent
    bit_depth = 8
    scale = 2 ** (bit_depth - 1)
    audio = np.round(audio * scale) / scale

    # 2. Downsample to 11025 Hz and back (loses high frequencies naturally)
    audio_low = librosa.resample(audio, orig_sr=sr, target_sr=11025)
    audio = librosa.resample(audio_low, orig_sr=11025, target_sr=sr)

    # 3. Band-pass filter: keep 150Hz – 5kHz (Minecraft's frequency range)
    from scipy.signal import butter, sosfilt
    sos = butter(4, [150, 5000], btype='band', fs=sr, output='sos')
    audio = sosfilt(sos, audio)

    # 4. Light hard-clipping for that digital edge
    audio = np.clip(audio, -0.8, 0.8)

    # 5. Normalize
    audio = audio / np.max(np.abs(audio) + 1e-8)
    return audio
```

**Evaluation method:**
- Generate 10 samples per prompt with different seeds
- Apply DSP chain
- Compare against real Minecraft sounds using CLAP similarity scores
- Tune DSP parameters (bit depth, cutoff frequencies, clipping threshold) to maximize similarity

**Compute:** Just inference time. ~5 min per batch of samples.

**Steps:**
1. Create a prompt template grid (5–10 templates × your existing captions)
2. Generate with vanilla AudioLDM2 at guidance scales [3.5, 5.0, 7.5]
3. Apply DSP chain with different parameter settings
4. Compute CLAP cosine similarity between outputs and real Minecraft sounds
5. Select best prompt template + DSP params

**Pros:** Zero training, instant results, great baseline for comparison, informative about what the remaining gap actually is.
**Cons:** Limited by what the pretrained model can produce; can't generate truly novel Minecraft-specific sounds.

## Approach 4: Train Small Model from Scratch on Discrete Tokens

**Core idea:** Bypass the pretrained model entirely. Tokenize your Minecraft sounds into discrete codes with EnCodec, then train a small text-conditioned transformer from scratch to generate those token sequences.

**Why it works:** The domain gap problem disappears — there's no pretrained distribution fighting you. A small transformer (10-50M params) can memorize and generalize from 325 clips in a restricted domain. Think of it like training a tiny GPT that "speaks" Minecraft sounds.

**Architecture:**

```
Caption → Frozen text encoder (CLAP or T5-small) → text embeddings
                                                          ↓
                                              Small causal transformer
                                                          ↓
                                              EnCodec token sequence
                                                          ↓
                                              EnCodec decoder (frozen)
                                                          ↓
                                                    Waveform
```

**Tokenizer — EnCodec:**
```python
from encodec import EncodecModel
from encodec.utils import convert_audio

# Load 24kHz EnCodec (or use 48kHz version)
encodec = EncodecModel.encodec_model_24khz()
encodec.set_target_bandwidth(1.5)  # 1.5 kbps → 2 codebooks × 75 tokens/sec

# Tokenize: 4s audio → 2 × 300 = 600 tokens
encoded = encodec.encode(audio_tensor)  # returns list of (codes, scale)
codes = encoded[0][0]  # shape: (1, n_codebooks, n_frames)
```

At 1.5 kbps bandwidth: 2 codebooks × 75 frames/sec × 4 sec = 600 tokens total.
At 6.0 kbps bandwidth: 8 codebooks × 75 frames/sec × 4 sec = 2400 tokens.
**Use 1.5 kbps** — fewer tokens = easier to learn, and the lower fidelity matches Minecraft.

**Text encoder — frozen CLAP or T5-small:**
```python
# Option A: CLAP (audio-aware text embeddings, 512-dim)
from transformers import ClapModel, ClapProcessor
clap = ClapModel.from_pretrained("laion/clap-htsat-unfused")
text_emb = clap.get_text_features(input_ids=...)  # (B, 512)

# Option B: T5-small (768-dim, sequence of embeddings for cross-attention)
from transformers import T5EncoderModel, T5Tokenizer
t5 = T5EncoderModel.from_pretrained("t5-small")
text_emb = t5(input_ids=...).last_hidden_state  # (B, seq_len, 768)
```

**Transformer — small causal decoder:**

| Component | Size |
|-----------|------|
| Layers | 8–12 |
| Hidden dim | 512 |
| Attention heads | 8 |
| FFN dim | 2048 |
| Codebook vocab | 1024 (EnCodec default) |
| Total params | ~20-30M |
| Context length | 600 tokens (4s at 1.5kbps) |

**Token interleaving (for multiple codebooks):**
With 2 codebooks, interleave tokens: `[c1_t1, c2_t1, c1_t2, c2_t2, ...]` — so the model produces 600 tokens in sequence. Alternatively, use the "delay pattern" from MusicGen (predict codebook 2 with a 1-step delay).

**Training:**

```python
# Pseudocode
for caption, audio in dataloader:
    # Encode text
    text_emb = frozen_text_encoder(caption)        # (B, seq_len, D) or (B, D)

    # Tokenize audio
    codes = frozen_encodec.encode(audio)            # (B, n_codebooks, T)
    tokens = interleave(codes)                      # (B, n_codebooks * T)

    # Causal LM forward pass with text conditioning
    logits = transformer(tokens[:, :-1], text_emb)  # (B, seq_len-1, vocab)

    # Cross-entropy loss
    loss = F.cross_entropy(logits.reshape(-1, vocab), tokens[:, 1:].reshape(-1))
    loss.backward()
```

**Training hyperparameters:**

| Parameter | Value |
|-----------|-------|
| LR | 3e-4 |
| Optimizer | AdamW (β1=0.9, β2=0.95) |
| Weight decay | 0.1 |
| Batch size | 16–32 |
| Epochs | 200–500 |
| Warmup | 5% of total steps |
| Scheduler | Cosine decay to 1e-5 |
| Dropout | 0.1 |

With 277 train clips, batch size 16, 300 epochs → ~5,200 steps. Should train in under an hour on a T4.

**Inference:**

```python
text_emb = frozen_text_encoder("minecraft zombie hurt sound effect")
tokens = [BOS]
for _ in range(600):
    logits = transformer(tokens, text_emb)
    next_token = sample(logits[:, -1], temperature=0.9, top_k=250)
    tokens.append(next_token)
codes = de_interleave(tokens)                     # (1, 2, 300)
audio = frozen_encodec.decode(codes)              # waveform
```

**Key implementation decisions:**
- **Text conditioning:** Use cross-attention (T5 gives sequence of embeddings) or concat a projected CLAP embedding as the first "token." Cross-attention is more powerful.
- **Sampling strategy:** Use top-k (250) + temperature (0.8–1.0). Lower temperature = more consistent but less varied.
- **Data augmentation still helps:** Your existing speed/gap augmentations give the model more token pattern variety.

**Compute:** ~20-30M param model trains in 30-60 min on T4. Very fast iteration.

**Pros:** No domain gap. Full control over architecture. Fast training. Low fidelity of EnCodec at 1.5kbps naturally matches Minecraft. Small model = easy to experiment with.
**Cons:** Training from scratch means no pretrained knowledge of general audio concepts. May produce less coherent audio without enough data. Requires implementing the transformer + training loop from scratch.

## Approach 5: Expand Dataset + Improved Diffusion Fine-tuning

**Core idea:** Stay with AudioLDM2 but fix the two main failure modes: insufficient data and suboptimal training strategy.

**Dataset expansion (target: 2000+ clips):**

| Source | Method | Expected yield |
|--------|--------|----------------|
| All Minecraft versions (1.0–1.21) | Fetch from `InventivetalentDev/minecraft-assets` for multiple version branches | ~500–800 unique sounds |
| Minecraft mod packs | Download popular modded sound packs (Faithful, BDcraft, etc.) | ~300–500 |
| YouTube gameplay | Download videos, apply Demucs/HTDemucs source separation to isolate SFX | ~500–1000 (noisy but plentiful) |
| Bootstrapping | Generate with approach 3 (prompt+DSP), filter by CLAP similarity > threshold | ~500 |

**Improved training recipe:**
- Use the **official AudioLDM2 fine-tuning script** from `diffusers` (`train_text_to_audio.py` in the examples folder) instead of a custom loop — it handles gradient scaling, EMA, and noise scheduling correctly
- Train with **SNR weighting** (Min-SNR-γ with γ=5) — this weights the loss to focus on the most informative noise levels, dramatically improving sample quality
- Use **EMA model averaging** (decay 0.9999) for stable generation
- Increase LoRA rank to 32–64 with a larger dataset (less overfitting risk)
- Train for 5000–10000 steps with effective batch size 8–16

**Compute:** Longer training on larger data. ~4-8 hours on T4 for 5000 steps.

**Pros:** Stays within your existing codebase. More data is the most reliable way to improve any model.
**Cons:** Data collection is labor-intensive. Still fighting the domain gap to some degree.

## Recommended Work Split

| Approach | Effort | New code needed | Best for |
|----------|--------|-----------------|----------|
| 1. Content + Style Transfer | Medium | Style transfer net | If AudioLDM2 gets content right already |
| 2. AudioGen/AudioCraft fine-tune | Medium | Rewrite train/infer | Strongest bet for quality with small data |
| 3. Prompt + DSP | Low | DSP chain only | Quick baseline, do this first regardless |
| 4. Small model from scratch | High | Full transformer + training | Most creative control, no domain gap |
| 5. Expand dataset + fix training | Medium-High | Data collection scripts | If you want to stay with AudioLDM2 |

**Suggested plan:** One person starts Approach 3 as a quick afternoon baseline, then moves to Approach 2. The other person tackles Approach 4. Compare results and pick the winner.
